# Fluxa 项目设计文档

> 状态：v0.0.1，尚未发版，讨论中。

## 1. 项目背景

- 定位：面向企业内部的 AI 资源分发管理系统。
- 场景：企业统一采购各类 LLM 的 Token/额度，通过系统分发给内部员工使用；员工在系统内直接调用，不需要自己单独申请供应商账号。
- 核心诉求：省钱可控（统一采购 + 配额管控）、好用（飞书登录、个人路由自定义）、安全（敏感信息不外泄）。

## 2. 目标与非目标

### 2.1 目标

- 员工能查看自己的使用记录（调用了什么模型、消耗多少、什么时间）。
- 员工能查看各类 LLM 的资费情况，判断用哪个模型更划算。
- 员工能在企业已启用的模型/供应商范围内，自由配置自己的调用路由（fallback 链、条件切换目标模型/供应商）——配额统一按金额计量，不区分具体用了哪个供应商/模型，怎么花是员工自己的事。
- 管理员能在后台统一管理所有数据（供应商、成员、配额、安全规则等）。
- 管理员能给指定用户手动调整配额，作为员工主动申请之外的另一条路径；企业规模变大后，也支持把配额委托到部门层级（部门总额度池，由部门负责人在池子内二次分配给成员）。
- 企业每次向供应商采购 LLM 额度都要有入库记录（供应商、时间、金额），和后续的配额分发、实际消耗形成完整的「入库 → 分发 → 消耗」台账，不能管理员凭感觉分发、账目对不上。
- 员工可以直接用已有的飞书账号登录，不需要额外开户。
- 对没有接入统一 IM 的企业，提供兜底的自建账号体系（手机号 / 邮箱注册登录）：开放自注册，注册后进入待审批状态，管理员事后审批通过才能使用；整个能力由管理员在后台开关控制是否启用，与 IM 登录并存、按企业情况二选一或共存。
- 敏感信息（如身份证号等）通过正则规则识别，命中后自动脱敏替换，而不是粗暴拦截拒绝整个请求。

### 2.2 非目标（明确不做）

- 不做多企业 SaaS 化。产品定位是每个企业自己部署一套独立系统，不是一套系统服务多家企业；不需要跨企业的数据隔离和计费结算设计。
- 暂不做海外场景：不实现海外 IM（Slack/Teams 等）身份源，不内置护照号/SSN 这类国际敏感信息类型的识别规则；身份源和敏感信息类型在架构上做成可扩展的插件式设计（留口子），但当前只覆盖国内场景（飞书/企业微信/钉钉、身份证号/手机号/银行卡号），不为海外场景投入额外设计成本。

## 3. 术语表

| 术语 | 说明 |
|---|---|
| 租户 (Organization) | 一个企业主体 |
| 部门 (Department) | 租户内的组织节点 |
| 成员 (Member) / 员工 | 归属某租户的用户 |
| 外部身份 (External Identity) | 飞书等平台颁发的身份，与本地成员绑定 |
| Provider | 企业采购的上游 LLM 供应商 |
| 全局路由规则 | 管理员维护的兜底路由/降级规则 |
| 个人路由规则 | 员工在企业已启用的模型/供应商范围内自由配置的路由/fallback 规则 |
| 虚拟 Key | 员工/项目对外发起调用的凭证，携带配额 |
| 配额 (Quota) | 一定周期内可消费的金额（¥/$）上限，统一按金额计量，不区分供应商/模型 |
| 入库记录 (Procurement Record) | 企业每次向供应商采购 LLM 额度的流水（供应商、时间、金额），是「入库 → 分发 → 消耗」台账的起点 |
| 部门总额度池 | 分配给某个部门的配额总量，由部门负责人在池子内二次分配给部门成员 |
| 部门负责人 | 管理本部门成员、审批本部门配额申请、在部门总额度池内分配额度的角色 |
| 配额申请/配额调整 | 员工主动申请（默认由部门负责人审批），或管理员/部门负责人主动调整 |
| DLP 规则 | 敏感信息识别与处理规则（脱敏替换 / 拦截 / 记录），对有校验位的类型（身份证号、银行卡号等）额外做格式校验 |
| 资费 (Pricing) | 各模型的计费单价信息；长期方向是接入供应商真实账单做对账，不只是静态价目表 |
| 权限点 (Permission) | 系统内可被单独授予的一项操作能力（例如「管理 Provider 凭证」「审批配额」「查看审计日志」） |
| 角色 (Role) | 一组权限点的集合，分配给成员；系统内置若干默认角色，后续可扩展/自定义 |
| 资源健康状态 | Provider/资源的可用性状态机：正常 → 熔断（隔离） → 半开（试探） → 恢复；超过失败阈值自动熔断，冷却后自动半开试探 |

## 4. 总体架构

- 员工侧：登录（飞书）→ 查看资费/用量 → 配置个人路由 → 发起调用 / 申请配额。
- 管理侧：管理供应商与全局路由 → 管理成员与配额（可直接管理，也可把配额委托到部门总额度池由部门负责人二次分配）→ 配置安全规则 → 查看审计。
- 请求处理链路：鉴权 → 安全过滤（敏感信息脱敏）→ 路由决策（个人路由优先，回落到全局路由，且不超出企业已启用的模型/供应商范围）→ 供应商调用 → 用量记录。
- 部署形态：前端打包进后端服务，作为单一部署单元交付给企业自部署，不额外维护前端服务。

## 5. 技术选型

- 后端：Golang。HTTP 路由用 chi——路由匹配开销跟标准库 net/http、gin 在同一量级（纳秒级），对网关请求转发延迟（由上游 LLM 调用主导，通常 200ms~5s）没有可观测影响，选它是为了 90+ 个接口的分组/中间件链（rbac/i18n/日志）写起来干净，而不是为了性能；底层就是标准 `http.Handler`，不锁定专有生态。真正影响网关性能的是流式响应不能被中间件缓冲（SSE 逐 token 转发要用 `http.Flusher` 及时 flush）和到上游供应商的连接复用（`http.Transport` 保活/连接池），这两点跟路由库选型无关，具体在 7.2 Provider 模块的网关链路里落地。
- 数据库：PostgreSQL，驱动用 pgx（lib/pq 已进入维护模式，不再选它）；数据访问层手写 SQL，不引入 ORM（GORM 这类会拖累部门池分配、熔断状态查询这类复杂条件查询的可控性），也不引入 sqlc 代码生成（当前团队规模下，多一道 codegen 步骤换来的类型安全收益不够）。
- 数据库 migration 工具：golang-migrate，纯 SQL 迁移文件（每个模块一对 up/down），CLI 和 Go library 都能跑，跟已经定好的「按模块前缀命名」直接契合。
- 前端：React + shadcn/ui，做定制主题/组件，不用官方默认样式。
- 部署架构：前端构建产物打包嵌入后端服务，对外只交付一个部署产物（单进程/单镜像），不需要单独部署前端服务，配合「企业自部署」的定位，降低部署门槛。
- 身份对接：飞书（后续可扩展企业微信 / 钉钉）；身份源做成可插拔的适配器设计，架构上不排斥以后接入 Slack/Teams 等海外 IM，但当前只做国内。

## 6. UI 风格与规划

> 本节的色板、圆角、图标、组件规则已经过高保真设计稿验证（管理员 16 屏 + 员工自助 4 屏 + 登录 3 屏，共 23 屏），可以直接作为前端开发的对照规范。

### 6.1 设计基调

- 定位是企业内部工具，不是面向消费者的营销产品：视觉上追求「克制、可信、高效」，不堆砌视觉装饰，优先保证信息密度和操作效率。
- 基于 shadcn/ui 组件库定制主题（色板、圆角、间距、字重），不用官方默认配色；是一套属于 Fluxa 自己的视觉方案，不沿用旧代码库那套已经推翻的样式。
- **默认浅色**，深色为可选主题（不是默认）：深色的 token 替换方式已验证，切换成本低，但浅色更符合企业内部工具的常规预期，作为默认呈现。
- 不支持企业自定义 Logo/主题色做二次品牌化：系统统一用 Fluxa 自己的默认视觉，每个企业各自部署一套独立系统，不是拿去做白牌/OEM 产品。
- 视觉上不是纯边框平贴的扁平感：卡片、顶栏组件（身份切换、通知铃）都带很轻的阴影做出层次，但不做重投影或玻璃拟态，保持克制。

### 6.2 视觉规范（色板 / 圆角 / 图标 / Logo）

**色板 —— 电钴蓝 Cobalt**（选型过程对比过电流青、熔金橙、洋红、纯极简灰阶等方向，电钴蓝在「不落入同类产品常见色相」和「足够克制、经得起企业场景长期使用」之间最平衡）：

| Token | 浅色（默认） | 深色（可选） |
|---|---|---|
| 强调色 accent | `#2F5FEA` | `#4B7CFF` |
| 强调色浅底 accent-soft | `#E9EEFF` | `#16233F` |
| 背景 bg | `#FFFFFF` | `#0A0B0D` |
| 侧边栏底 side-bg | `#F7F8FA` | `#0E0F12` |
| 卡片面 surface | `#FFFFFF` | `#16171B` |
| 边框 border | `#E2E4E9` | `#24262B` |
| 正文 ink | `#0A0B0D` | `#F2F3F5` |
| 弱化文字 muted | `#6B7078` | `#8B909B` |
| 成功 ok / 浅底 | `#1E7A4E` / `#E3F2E9` | `#4FBE85` / `#12281D` |
| 警示 warn / 浅底 | `#9A5E23` / `#F5E6D3` | `#D99A4E` / `#332812` |
| 危险 bad / 浅底 | `#C23B3B` / `#FBE6E6` | `#E5695F` / `#2E1917` |

语义色（成功/警示/危险）和品牌强调色是两套独立的色相，不复用——避免「熔断」状态和品牌色混淆。

**圆角**：整体容器（页面外框）12px，卡片/KPI/输入框/按钮 8px 上下浮动到 6px（小尺寸控件），身份切换 / 状态 pill 用 20px 全圆角胶囊。不同尺寸的圆角比例保持一致，不混用直角和大圆角。

**阴影**：卡片和顶栏组件用一层极轻的阴影（浅色下约 `0 1px 2px rgba(16,24,40,.05)`），整体容器再叠一层更大范围的柔和阴影做「悬浮在页面上」的层次感；深色下用极淡的内描边代替阴影（深色背景下投影不明显，用高光边替代）。

**图标**：线性描边风格，16px 基准、统一 1.5px 描边、圆角端点（round cap/join），不用面性填充图标，激活状态图标变强调色、非激活态用 muted 灰。管理员侧边栏 16 个导航图标 + 员工侧边栏 4 个导航图标 + 顶栏（通知铃、身份切换下拉箭头）+ 页面内操作图标，全部遵循同一套描边规则，不混用不同风格的图标库。

**Logo**：几何构成的「F」字标——三个矩形拼接而成，不是抓取某个字体的字形。定稿的构造画在 32×32 画布上：字高 20（y 6→26）、笔画 4.6（占字高 23%，一个扎实的 Bold）、横臂顶边在 13.1、**端点全部为直角，任何位置都不倒圆角**。字形盒 x 8.5..23.5 / y 6..26 在画布里已经是光学居中的，所以任何尺寸下都不需要再做二次对位。

方头（而不是圆角）是刻意的：Fluxa 是自托管、跑在客户机房里、面向工程和 IT 的基础设施，直角的体温比圆角更准；圆角是这几年 SaaS 的通用语，拿不到识别度。

两种形态，同一个字形：**裸标记**（`LogoMark`，强调色实心，用于需要和「Fluxa」字样并排的场合）和**徽标**（`Logo`，圆角方底 + 反白字标，用于侧边栏、登录页、favicon）。徽标里字标缩放到 0.7，字高约占徽底 44%；反白色恒为纯白，不走 `primary-foreground`（该 token 在深色下是近黑，会把字标翻成黑色）。这是 Fluxa 唯一的品牌视觉，不支持替换。

**供应商 / 模型标识、登录方式、发信通道**：改为使用各厂商的真实品牌图标（飞书、钉钉、OpenAI、Anthropic、Azure、AWS Bedrock、阿里云等），不再统一走字母头像——真实图标更直观，登录按钮、身份源、供应商列表这类场景一眼就能认出对应的厂商。图标来源经过筛选，只用能明确重新分发的：飞书/钉钉取自厂商官方 Linux 客户端安装包内置的图标；OpenAI/Anthropic/Azure/Gemini/Bedrock/阿里云取自 lobehub/lobe-icons（MIT 协议）。企业微信目前没找到可用来源（Simple Icons、lobe-icons 都没收录，也没有官方 Linux 客户端可提取），暂时还是用字母头像占位。这条决定推翻了早前「统一用字母头像，避免品牌使用问题」的结论——但那个顾虑并非空穴来风：Simple Icons 的 OpenAI 图标就是被官方要求下架的，选源上必须谨慎，不能什么图随手就用。

### 6.3 信息架构

- 管理员视角和员工视角共用同一套系统，靠 RBAC 控制导航项和操作权限的可见性，不拆成两个独立的 App。
- **管理员视角**（侧边栏按分组组织，共 16 个页面）：
  - 顶层：概览、快速接入（API 文档）。
  - 资源管理：供应商、模型与路由、Playground（模型演练场）、入库记录。
  - 组织与权限：成员与部门、角色权限、Key 管理、身份源、短信 / 邮件配置、审批通道。
  - 安全：DLP 规则、安全事件。
  - 审计：调用日志、操作审计。
- **员工自助视角**（精简侧边栏，共 4 个页面）：我的用量、资费一览、我的路由配置、配额申请；如果是部门负责人，还能在「配额申请」页看到本部门的分配和审批。
- **登录页**独立于主框架之外：不带侧边栏/顶栏，左右两栏——左栏是登录表单（固定 340px measure，居中于左半区），右栏是产品价值轮播（四屏，对应 2.1 的四个目标）。**登录页不带版权信息栏**——版本号/版权/许可证是控制台的机箱信息，压在这一屏只是和表单抢注意力，这一屏只问一件事。飞书登录为主按钮，手机号/邮箱登录为次要入口。**左栏按钮不是写死的**：渲染哪几种方式由 `/api/auth/methods` 决定，管理员没开通的方式不出现，一种都没开通时给出明确说明而不是空白。右栏是纯装饰（`aria-hidden`），窄屏（≤900px）整栏隐藏，登录路径不受影响。
  - 右栏没有采用同类产品常见的实景照片：Fluxa 跑在客户自己的机房里，没有可拍的使用场景，摆一张办公室图库照说不出任何真话。改为用自己的品牌 token 画——电钴蓝深化的渐变 + 当前那屏图标的超大低透明度水印，文字压在底部。
  - 三屏拆分沿用：入口选择、手机号/邮箱表单、注册后待审批。**没有「飞书扫码」屏**——飞书 OAuth 是整页跳转到飞书自己的授权页，二维码由飞书渲染，我们再画一个就是画一个不存在的东西。
- 导航结构：侧边栏做主导航，顶部放身份切换（同一个人可能既是部门负责人又是普通员工）和通知入口；侧边栏底部固定成员身份区（头像 + 姓名 + 角色），内容区底部固定一条版权信息栏（版本号 + 版权 + 项目仓库链接），不随内容滚动。
- 核心页面类型收敛成七种，全站复用同一套组件范式，不为每个页面单独设计：
  - **列表/表格页**（供应商、模型、入库记录、DLP 规则、安全事件、调用日志、操作审计、Key 管理）：筛选行（搜索框 + 下拉筛选）+ 表格 + 行内操作。
  - **仪表盘/图表页**（概览、我的用量）：KPI 卡片行 + 图表 + 多卡片网格。
  - **两栏主从页**（成员与部门、角色权限）：左侧窄列表（部门/角色）+ 右侧对应内容（成员表格 / 权限勾选矩阵）。
  - **链式配置页**（我的路由配置）：条件 → 目标模型 → 备用模型的可视化链条，而不是一张扁平表格。
  - **表单页**（配额申请）：左侧填写表单，右侧展示自己的历史申请记录和状态。
  - **对话测试页**（Playground）：左侧对话框直接跟选中的模型交互，右侧一栏请求诊断（延迟、Token、费用、命中的供应商、Request ID），用于验证 Provider/路由是否真的生效。
  - **文档/说明页**（快速接入）：Base URL、认证方式、代码示例（curl / Python 等），配合「创建我的第一个 Key」的引导。身份源、短信 / 邮件配置、审批通道三个页面共用列表/表格页的卡片变体（每项一张卡片 + 启用开关 + 编辑入口），不单独立类型——这三者本质是同一件事：一组可插拔适配器的配置。

### 6.4 语言与终端适配

- 默认简体中文；但前端架构上要预留 i18n 框架（文案走 key 而不是硬编码中文），方便以后加英文，不用推倒重来——只是暂不投入实际翻译、多语言内容维护的成本，呼应「暂不做海外场景」的决定。
- 桌面优先：管理员的配置类操作默认在电脑上完成；员工自助端（看用量、申请配额）做响应式适配，能在手机浏览器上用，但不做原生 App 或独立的移动端设计。

## 7. 模块设计

### 7.1 User 模块（租户与身份）

- 职责：管理组织、部门、成员；基于 RBAC（角色 = 权限点集合）模型管理成员权限，内置超管/管理员/部门负责人/员工等默认角色，同时支持管理员自定义角色（按需拆出 finance、security 这类专项角色），不锁死在内置角色里；接入飞书身份，并提供「身份源」配置页——管理员在后台填入各 IM 的 OAuth 应用凭证（App ID / App Secret）和回调地址，不是写死在配置文件里；在没有统一 IM 的企业里，提供开放自注册 + 管理员事后审批的本地账号体系（手机号/邮箱，管理员开关控制是否启用整个能力），配套「短信 / 邮件配置」页——短信和邮件都做成可插拔的发信通道（服务商、AccessKey/SMTP 凭证、签名/模板、启用开关），不写死某一家服务商，本地账号注册的验证码就是从这里发出去的；管理部门负责人角色与部门总额度池；向员工提供自己的用量与资费视图。
- 关键实体：组织、部门、成员、外部身份绑定、身份源配置（App ID/Secret、回调地址、启用开关）、本地账号（手机号/邮箱 + 凭证）、短信/邮件发信配置（服务商、凭证、签名/模板、启用开关）、登录方式开关、部门负责人、部门总额度池、权限点、角色（内置 + 自定义）。
- 待明确点：RBAC 的权限点具体怎么拆分（拆多细、要覆盖哪些操作）；本地账号与 IM 账号的合并/迁移策略（比如员工先用本地账号，企业后来才接入飞书，两边账号怎么关联到同一个成员）；员工没有归属部门、或部门没有设部门负责人时，配额申请审批兜底给谁；短信/邮件发信要不要预置国内主流服务商模板（阿里云短信、腾讯云短信），还是完全自定义 API 地址。
- 会话机制：登录成功后用服务端 Session 维持登录态，Session 存 Postgres（不额外引入 Redis，保持部署形态干净），后端每次请求查一次 Session 表；换来的是管理员封禁/踢人立即生效，符合企业内部工具「管理员要能马上收权限」的预期——这类请求是管理页/自助页的访问，不是网关转发热路径，多一次索引查询可以接受。

### 7.2 Provider 模块（资源管理）

- 职责：管理企业统一采购的 LLM 资源（供应商、模型、资费）；记录每一笔采购入库（供应商、时间、金额），形成「入库 → 分发 → 消耗」的完整台账；向员工/部门分发配额；展示各模型资费；支持员工在企业已启用的模型/供应商范围内自由配置个人路由规则；对 Provider/资源做健康熔断与自动恢复（半开试探机制），保障路由的鲁棒性，不只是静态的降级顺序；提供 Playground（模型演练场），配置好供应商/模型/路由之后能就地发一条测试消息，验证真的接通、看清楚这次调用实际命中了哪个供应商，而不是配完就只能等真实业务流量去踩坑；提供 Key 管理页面，管理员和员工都能创建/查看/吊销虚拟 Key，Key 的归属单位是成员或部门总额度池，不引入独立的「项目」实体（对比过同类产品用「项目」做归属单位的做法，我们保持部门制的简单性，避免多引入一层归属关系）。
- 关键实体：Provider、模型资费信息、采购入库记录、全局路由规则、个人路由规则、虚拟 Key（配额载体，归属成员/部门，DB 只存哈希不存明文）、部门总额度池、资源健康状态（正常/熔断/半开）、审批通道配置（通道类型、凭证/地址、启用开关）。
- 待明确点：是否需要支持管理员对特定员工/部门做例外的供应商白名单限制（默认所有人共享同一份已启用供应商列表）；fallback 链要不要加成本熔断机制，防止员工配置出意外的高额路由，把配额快速消耗完；熔断阈值、冷却时间是否可配置，是否要分 Provider/模型单独设置；入库记录和配额分发之间要不要做软告警/硬校验（见开放问题）。
- 鉴权与一致性：虚拟 Key 校验是网关转发的真正热路径——DB 只存 Key 的哈希，校验先查短 TTL 内存缓存（如 30~60 秒），未命中才查库，吊销 Key 最多延迟一个 TTL 周期生效。部门总额度池余额不额外存冗余字段，用「初始池子 - 部门下所有成员当前配额之和」实时聚合计算，从根上避免跟「成员配额」表对不上账；概览页这类低频展示场景在聚合结果上加一层短 TTL 内存缓存，减少重复查询——网关转发时真正校验的是虚拟 Key 自己的额度（单行事务扣减），不查这个聚合值，缓存的陈旧数据不影响配额执行的准确性。

- 审批通道（可插拔）：配额申请里「审批」这一步做成可替换的通道——站内审批是默认实现，飞书审批、企业微信、钉钉、自建 OA 各是一个适配器，形状对齐 7.1 的身份源和 notify 的发信通道，加一家是加一个文件，不是改流程。但审批和这两者有本质差别：换码和发信都是同步、无状态、一次性的，审批是一次跨越小时到天的往返，外部有一个我们不拥有的状态机，回程机制还各家不同（长连接 / webhook / 只能轮询）。所以接口拆成两半：出站的提单 / 查单 / 撤单走统一的 Channel 接口，回程的推送解析做成可选的 Inbound 接口——没有推送能力的通道靠查单轮询，功能不打折，只是慢。把回程硬塞进同一个接口，会逼着只能轮询的通道去假装自己有推送。
  - **轮询是保底，推送是优化**：对账循环（定时扫超时未更新的待处理单子逐个查单）是必做项，推送后加。三条理由各自独立成立——自建 OA 可能只有查询接口没有推送；推送会因网络、重启、订阅过期而丢；最要紧的是这样一来「企业不开公网回调地址」是一等支持路径而不是降级方案，直接化解 7.1 里那条 webhook 约束。这条和直觉相反（直觉是先做 webhook），但它决定了自建 OA 能不能接得进来。
  - **能力描述符**：每个通道声明自己支不支持由 Fluxa 指定审批人、能不能撤单、有没有推送、推送要不要公网地址、无推送时的对账间隔。前端读它决定「撤回申请」按不按得亮、要不要提示「结果最长延迟 N 分钟」。没有它，UI 只能按最弱通道设计，或者按最强通道设计然后骗人。
  - **坚决不抽象外部系统的流程动作**：转交、加签、退回、催办、抄送一个都不进领域模型。外部回来的东西归一化成四态结果（待处理/通过/驳回/撤回）加一段纯展示的进度文字；只有结果驱动状态机，进度文字不驱动任何逻辑。想把每个平台的流程都建模进来，是这类集成的头号死法。配额申请的状态只增加「已撤回」一种（对方撤回），长期无响应做成展示标记而不是新状态——单子仍然是待处理，等人来看，系统不自作主张改判。
  - **不需要额度预占 / 冻结**：异步审批落地时可能超出部门额度池，但本节「鉴权与一致性」已经决定余额实时聚合、不落库，且负数是允许且有意义的（同 8.1 入库记录的口径：v1 信任管理员，宁可让人看见真实数字，也不静默拦下一个会超支的审批）。既然超支可见且被接受，就不构成状态不一致，只是一个负数——整套冻结 / 释放 / 超时回收机制因此都不需要。
  - **幂等是唯一真正会出事的地方**：正因为不做冻结，最大风险变成同一个「通过」被应用两次、额度多给一份。(通道, 外部单号) 建唯一索引，存最后一次事件 ID 与决定时间，应用时比对决定时间、不比现有记录新的直接丢弃。推送和轮询同时送达同一个结果是正常路径不是异常，应用逻辑必须天然幂等。
  - **自建 OA 靠发布契约，不靠逐家写适配器**：出站 POST 一段带签名的 JSON、期望回一个外部单号；回程二选一——对方推到我们的回调地址，或者我们按配置的 URL 定时拉。签名统一 HMAC-SHA256(secret, 时间戳 + nonce + body)，时间戳偏差超过 5 分钟拒收、nonce 去重。拉取模式不需要企业开放任何公网入口。
  - **默认实现必须走同一个接口**：站内审批本身也实现成一个通道，这样「没接外部 OA」不是特例分支，而是同一条代码路径。否则半年后外部通道那条路径会因为平时没人走而腐烂。
  - 接入顺序：v1 先接飞书（企业已经在用飞书登录，App 凭证和通讯录都现成），自建 OA 的通用契约同期定义好；企业微信、钉钉留空文件占位，按需补。注意飞书审批定义不能由 Fluxa 创建，部署时需要企业管理员先在飞书审批后台建好定义、再把 approval_code 填进「审批通道」配置页——这是一条新的部署前置步骤。另有一处待确认：飞书审批的事件订阅是应用级（长连接 / 回调）还是用户级，直接决定推送这条优化路径成不成立（见开放问题 8）；对账轮询不受影响。

### 7.3 Security 模块（安全管理）

- 敏感信息识别：基于正则规则识别身份证号等敏感模式，只覆盖员工发出去的请求内容，LLM 返回的响应不扫描——直接呼应「流式响应不能被中间件缓冲，要用 http.Flusher 及时 flush」的网关性能原则，响应扫描要么破坏流式转发要么要做跨 chunk 滑动窗口扫描，v1 不为「模型在回复里意外复述敏感信息」这种低概率场景背上这个复杂度和延迟成本，留给 v2 视情况评估；对有校验位的类型（身份证号 18 位校验码、银行卡号 Luhn 算法等）额外做格式校验，减少形似但无效的误报。敏感信息类型做成可插拔的规则定义，当前只内置国内类型（身份证号、手机号、银行卡号），护照号/SSN 等国际类型留了扩展口子但不实现。
- 处理方式：命中后自动脱敏替换（mask），继续放行请求，而不是直接拒绝；同时保留日志记录。
- 待明确点：脱敏后的展示形式（例如是否保留首尾若干位）；是否所有敏感类型都用脱敏，还是有更高风险类型需要直接拦截。

## 8. 关键流程

### 8.1 采购入库

- 管理员每次向供应商采购 LLM 额度后，在后台录入一条入库记录（供应商、时间、金额）。
- 入库记录只做台账登记，v1 阶段不与配额分发总量做强制校验（不阻止超发），但为后续对账和软告警留下数据基础。

### 8.2 员工登录与身份绑定

- 员工用飞书扫码登录；系统换取身份信息后，按策略自动开通或转入待审批队列。
- 已有账号的用户可以主动绑定飞书身份，绑定后可直接扫码登录。

### 8.3 本地账号注册（无统一 IM 的企业）

- 员工用手机号/邮箱开放自注册；提交后账号进入待审批状态，暂不可用。
- 管理员事后审批通过，账号才正式激活，可以登录使用。

### 8.4 配额申请与调整

- 员工可主动提交配额申请（模型/额度/用途/期限）；默认由所在部门的部门负责人审批，没有归属部门或部门没有负责人时转由管理员兜底审批。
- 审批这一步走「审批通道」（见 7.2）：默认是站内审批，管理员也可以把它切到飞书审批 / 企业微信 / 钉钉 / 自建 OA。切到外部通道后，Fluxa 仍然是这张单子的系统记录方——员工照样在 Fluxa 填表提单，Fluxa 把它投递到外部系统拿回一个外部单号，外部的决定回来后归一化成通过/驳回/撤回三种结果落到本地状态；外部系统只是被授权做那个决定，不接管单据本身。结果回程以定时对账为准、推送为加速，因此外部系统即便没有推送能力也能接。
- 审批通道切到外部后，管理员端的待办入口只保留只读跟踪，不再提供站内的通过/驳回按钮——同一张单子两边都能操作会产生冲突，谁先落谁生效这种规则解释成本高于收益。
- 管理员可以直接在后台给指定用户调整配额，不需要经过申请流程；部门负责人也可以在本部门总额度池范围内直接调整成员配额。这条路径不走审批通道，不受上一条影响。

### 8.5 安全过滤链路

- 请求内容先做敏感信息识别 → 命中正则规则的部分做脱敏替换 → 处理后的内容再进入路由与供应商调用。

## 10. 路线图

规划原则：v1 一次性做成员工能自助使用、管理员能统一管控的完整核心版本，不分阶段阉割成「先给管理员用、员工只能被动等分配」的半成品；再逐步把「企业级治理与深度安全」这类锦上添花的能力补上。

### v1 —— 核心版本（管理员管控 + 员工自助，一步到位）

- **Provider**：多供应商接入、统一对外入口、全局路由与降级规则；员工个人路由规则（在企业已启用的模型/供应商范围内自由配置 fallback / 条件切换）；Provider/资源具备健康熔断与自动恢复（半开试探）机制，不是简单的静态降级顺序；各模型资费信息展示，员工自己能判断怎么用更划算；Playground 模型演练场，配好就能就地测试、看清命中了哪个供应商；Key 管理页面，Key 归属成员/部门，不引入项目概念。
- **User**：组织/部门/成员、飞书登录（后续可扩展企业微信、钉钉），配套身份源配置页（管理员在后台填 App ID/Secret 和回调地址，不写死在配置文件里）；RBAC 模型（角色 = 权限点集合），内置超管/管理员/部门负责人/普通员工等默认角色，同时支持管理员自定义角色；部门总额度池 + 部门负责人角色，管理员可以把配额委托到部门，由部门负责人在池子内二次分配；本地账号兜底体系（手机号/邮箱开放自注册 + 管理员事后审批，整体能力由管理员开关控制），解决没有统一 IM 的企业；短信 / 邮件发信配置页，把注册验证码的发信通道做成可插拔配置（服务商、凭证、签名/模板），不写死在代码里；通讯录同步（部门/成员自动从飞书同步），默认走定时拉取、周期可配置（默认较短，比如每小时一次），管理员也可以随时手动触发立即同步，离职/权限变更这类高风险场景靠短周期兜底；只有企业愿意开放公网可达的回调地址时才额外支持 webhook 实时同步，作为可选增强。
- **配额**：虚拟 Key + 预算，统一按金额计量；管理员可以直接给成员分配/调整配额，也支持委托到部门总额度池由部门负责人二次分配；员工自助配额申请 + 审批流程（默认由部门负责人审批，没有部门/负责人时管理员兜底），和管理员/部门负责人直接调整并存为两条路径；审批这一步做成可插拔的「审批通道」（见 7.2），v1 落地站内审批（默认）+ 飞书审批两个通道，同期把自建 OA 的通用签名契约定义出来，企业微信/钉钉留接口占位——关键是底层的往返模型（出站提单 / 对账查单 / 可选推送 / 能力描述符）v1 就要立住，后面加一家是加一个适配器文件而不是改流程；每次采购都要录入入库记录（供应商、时间、金额），但入库总量与分发总量之间 v1 阶段不做强制校验，完全信任管理员自行把控——先把账记全，卡点留到后面版本再加。
- **可见性**：员工能看自己的使用记录（模型、用量、时间）和各模型资费。
- **Security**：基于正则的敏感信息识别，对有校验位的类型（身份证号、银行卡号）做格式校验减少误报，命中后脱敏替换或拦截，内置一套基础敏感词规则（身份证号、手机号、银行卡号等）。
- **审计**：调用日志留存。
- **UI**：默认浅色，深色为可选主题；统一使用 Fluxa 自己的默认视觉（电钴蓝色板 + 几何 Logo），不支持企业自定义 Logo/主题色做二次品牌化。

v1 目标是交付一个完整可用的系统：员工飞书登录即用，能看用量和资费，能自己配路由，能自己申请配额；管理员能统一管控，也能把配额委托给部门负责人分担；没有统一 IM 的企业也能用本地账号跑起来。不是一个只有管理员能用、员工被动等分配的阉割版。

### v2 —— 企业级治理与深度安全

- 异常用量检测与告警（先做阈值规则，不做机器学习异常检测）。
- 操作审计日志（管理操作留痕，区别于调用日志）。
- 敏感词库分层：v1 内置词库的基础上，支持租户自定义词库，评估是否接入第三方合规词库。
- 本地账号与 IM 账号的合并策略正式落地。
- 视需要支持多级/按金额分级的审批链（在 v1 简单审批流的基础上）；接外部审批通道的企业，这一层由对方的审批流承担，Fluxa 不重复建模。
- 审批通道补齐企业微信、钉钉适配器（v1 已留好接口和空文件，按客户需求排期）。
- 账单对账（长期方向）：接入供应商真实账单，核对内部用量记录与实际花费是否一致，逐步替代 v1 阶段「完全信任管理员」的粗放模式。

## 11. 待确认的开放问题

1. 异常用量检测后是否自动封禁？（v2）
2. 敏感词库来源：内置 vs 接入第三方？（v1 先用内置词库，v2 评估分层与第三方接入）
3. 脱敏替换的具体规则：不同敏感信息类型的脱敏格式（例如身份证号是否保留部分位数）是否需要可配置？—— v1 就要定，因为 v1 已经包含脱敏能力。
4. 本地账号从 v1 就有，但和 IM 账号的正式合并策略要到 v2 才落地：按手机号/邮箱自动匹配，还是要走人工绑定确认？短信/邮件发信配置页 v1 就有（可插拔，不写死服务商），但具体先预置哪家服务商的模板（比如阿里云短信/腾讯云短信）还没定。
5. 个人路由的 fallback 链要不要加成本熔断机制，防止员工配置出意外的高额路由，把配额快速消耗完？—— v1 就要定，因为个人路由从 v1 就有。
6. 资费信息 v1 阶段先手动维护；长期方向已定为对接供应商真实账单做对账（v2+），但具体先对接哪家（阿里云 / OpenAI / Anthropic 账单）、多久同步一次还没定。
7. v1 有了入库记录之后，要不要在 v2 加一个「分发总量超过入库余额」的软告警（先不做硬校验）？有了台账，加告警的成本比 v1 阶段低很多。
8. 飞书审批的事件订阅是应用级（长连接 / 回调）还是用户级？—— 直接决定推送这条优化路径成不成立：用户级订阅绑在具体人身上，服务端产品拿不到每个人的 token，人一离职订阅就断。对账轮询不受影响（那是保底路径），所以这个问题不阻塞 v1 接入飞书，但要在动手前查清，否则推送会做成一个半年后悄悄失效的功能。
9. 审批通道切到外部后，员工在 Fluxa 侧还能不能撤回自己的申请？—— 取决于通道的能力描述符（有的外部系统不支持程序化撤单）。倾向是：能力支持就给按钮，不支持就不显示，而不是给一个会失败的按钮。
10. 一个组织能不能同时启用多个审批通道（比如按部门或按金额分流）？—— v1 先做成组织级单选，避免"这单该走哪条"的规则解释成本；但配置实体上留了通道列表的结构，以后要扩不用改表。

## 12. 代码骨架

> 目录结构直接对照第 7 节的三个业务模块（User / Provider / Security），不多加模块；gateway（请求代理链路）、audit（审计）、notify（发信通道）、rbac（权限中间件）、platform（基础设施）是贯穿这三个模块的支撑层，不是独立的第四个业务模块。前后端各自成包但只交付一个产物，呼应第 5 节「前端打包进后端服务」的决定。

- 每个业务模块内部统一四层：`types`（实体）→ `repo`（PostgreSQL 存取）→ `service`（业务逻辑）→ `handler`（HTTP 层），每层各自成包；管理员视图和员工自助视图复用同一套 handler，靠 `rbac` 中间件控制导航项和操作的可见性，不拆两套接口（呼应 6.3 信息架构「不拆成两个独立的 App」）。
- 四层内部统一是「根文件只放装配，其余每个文件一个功能」：`repo.go` / `service.go` 里只有根接口（内嵌全部子接口）、唯一的实现结构体和构造函数，构造函数返回接口而不是结构体指针；`handler.go` 里只有 `Handler` 结构体、构造函数和路由表（`RegisterRoutes`），任何一个 endpoint 的实现都不写在这里。其余文件各承载一个功能：`repo` / `service` 里是一个独立子接口加它的实现，`handler` 里是那组 endpoint，`types` 里是那个实体。同一条约定也适用于非四层的包——`gateway/pipeline.go` 只有 `NewPipeline` 和路由表，`user/session/session.go` 只有 `Manager` 和构造函数。
- 四层的文件名一一对应：`provider` 模块的 `types/model.go`、`repo/model.go`、`service/model.go`、`handler/model.go` 讲的是同一件事，认准一个文件名就能纵向读完一条链路。加一块功能是加一组文件，而不是往几百行的文件末尾追加方法；模块之间、层之间依赖到的都是接口，测试可以直接替换实现。`handler` 层不需要接口——它没有第二种实现。
- `frontend/src/pages` 按 `admin/`（16 页）、`employee/`（4 页）拆分，一一对应 6.3 信息架构；`components/` 对应 6.3 收敛出的「七种页面类型」共享范式（表格页/仪表盘/两栏主从/链式配置/表单/对话测试/文档说明），不为每个页面单独起一套组件。
- `frontend/` 构建产物最终用 `go:embed` 打进后端二进制（`web/embed.go`），对外只交付一个部署产物，不单独部署前端服务；`frontend/` 本身仍是可以独立跑 dev server 联调的普通 React 项目。
- `migrations/` 按模块前缀命名（`user_*` / `provider_*` / `security_*`），用 golang-migrate 的纯 SQL up/down 文件；HTTP 路由用 chi，`handler` 包里都是标准 `http.Handler`，不依赖 chi 专有类型，换路由库的迁移成本很低。选型依据见第 5 节——路由匹配开销跟具体选哪个库无关（纳秒级，远小于上游 LLM 调用的毫秒~秒级延迟），真正影响网关转发性能的是流式响应 flush 和上游连接复用，这两点跟路由库无关，在 `gateway/pipeline.go` 和 `provider` 模块里落地，不会因为选了 chi 就打折扣。
